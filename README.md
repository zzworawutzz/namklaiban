# น้ำใกล้บ้านฉัน

ดูระดับน้ำจากสถานีวัดที่ใกล้บ้านที่สุด ข้อมูลจาก ThaiWater (สสน.) ใช้ประกอบการตัดสินใจเท่านั้น ไม่ใช่ประกาศทางการ

| ไฟล์ | หน้าที่ |
|---|---|
| `ingest.py` | ดึงข้อมูล ThaiWater → ฐานข้อมูล, ลบข้อมูลเก่าเกิน 31 วัน, บันทึกผลการรัน |
| `db.py` | ชั้นเชื่อมต่อ: SQLite (ในเครื่อง/เทสต์) หรือ Postgres เมื่อมี `DATABASE_URL` |
| `core.py` | ตรรกะอ่านข้อมูล: stale, แนวโน้ม, เวลาถึงตลิ่ง, คำแนะนำ, ต้นน้ำ/ปลายน้ำ |
| `api.py` | FastAPI + endpoint `/api/cron/ingest` (ป้องกันด้วย `CRON_SECRET`) |
| `notify.py` | แจ้งเตือนเมื่อสถานะสถานีใกล้บ้านเปลี่ยน (LINE) |
| `public/` | หน้าเว็บ (Leaflet) + PWA (Vercel เสิร์ฟจาก CDN) |

## รันในเครื่อง
```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
.venv/bin/python ingest.py
.venv/bin/uvicorn api:app --reload      # เปิด http://127.0.0.1:8000
.venv/bin/python -m pytest
```
ตั้ง cron ให้รัน `ingest.py` และ `notify.py run` ทุก 20 นาที

## API
`/health` · `/stations?province=&status=` · `/stations/nearby?lat=&lng=` · `/stations/{id}/readings?days=` · `/stations/{id}/related`

ฟิลด์เพิ่มของสถานี: `trend` (rising/falling/steady), `trend_pct_per_hr`, `eta_to_bank_h`, `advice`, `watch_pct`, `alert_pct`
- แนวโน้มคำนวณจากการวัดย้อนหลัง 6 ชม. ต้องมีข้อมูลห่างกันอย่างน้อย 45 นาที ถึงจะมีค่า
- `eta_to_bank_h` เป็นการต่อเส้นตรงจากอัตราปัจจุบัน ไม่ใช่การพยากรณ์
- `/related` แยกต้นน้ำ/ปลายน้ำจากระดับท้องน้ำของสถานีที่อยู่แม่น้ำเดียวกันในรัศมี 150 กม. เป็นการประมาณ

## Threshold ต่อสถานี
คัดลอก `thresholds.example.json` เป็น `thresholds.json` แล้วรัน `python ingest.py --thresholds thresholds.json` (ค่าเริ่มต้น 70% เฝ้าระวัง / 90% เตือนภัย)

## แจ้งเตือน LINE
1. สร้าง LINE Official Account เปิด Messaging API แล้วออก channel access token
2. `export LINE_CHANNEL_TOKEN=...`
3. `python notify.py add --channel line --target <LINE userId> --lat 14.2 --lng 99.0 --label บ้าน`
4. `python notify.py run` (ใส่ cron ต่อจาก ingest)

ลองโดยไม่ต้องมีบัญชีได้ด้วย `--channel stdout` แจ้งครั้งแรกเฉพาะเมื่อสถานีอยู่ที่เฝ้าระวัง/เตือนภัยแล้ว หลังจากนั้นแจ้งทุกครั้งที่สถานะเปลี่ยน

## แจ้งเตือนผ่าน LINE แบบให้ผู้ใช้สมัครเอง (webhook)
ผู้ใช้ส่ง **ตำแหน่งบ้าน** ให้บอตใน LINE (กด + → ตำแหน่งที่ตั้ง) ระบบเก็บ userId กับพิกัด แล้วแจ้งเตือนเมื่อสถานีใกล้บ้านเปลี่ยนสถานะ พิมพ์ "สถานะ" ดูค่าล่าสุด หรือ "ยกเลิก" เพื่อลบข้อมูล
ตั้งค่า:
1. env บน Vercel: `LINE_CHANNEL_TOKEN`, `LINE_CHANNEL_SECRET` (Basic settings ของ channel), ถ้าต้องการจำกัดจำนวนผู้ใช้ `MAX_SUBSCRIBERS` (ค่าเริ่มต้น 50)
2. LINE Developers → Messaging API → **Webhook URL** = `https://<โดเมน>/api/line/webhook` → Update → เปิด **Use webhook** → กด **Verify** ต้องได้ Success
3. ปิด **Auto-reply messages** และ **Greeting messages** ใน LINE Official Account Manager (ไม่งั้นข้อความซ้อนกับของระบบ)
ระบบตรวจ `X-Line-Signature` ทุกคำขอ จึงมีแต่ LINE ที่สมัครให้ผู้ใช้ได้ ควรมีหน้านโยบายความเป็นส่วนตัวก่อนเปิดให้คนทั่วไปใช้ เพราะเก็บตำแหน่งบ้าน

## รายงานสถานการณ์น้ำ
- **หน้าเว็บ** `/report.html?province=พระนครศรีอยุธยา` — ตัวเลขเตือนภัย/เฝ้าระวัง/ปกติ พร้อมการเปลี่ยนแปลงจาก 24 ชม. ก่อน, สถานีที่ล้นตลิ่งใหม่, กราฟจำนวนสถานีตามสถานะรายวัน, น้ำสูงสุด 10 อันดับ, สถานีที่ขึ้นเร็ว และปุ่มคัดลอกข้อความ/พิมพ์
- **API** `GET /reports/{จังหวัด}?days=14` (ชื่อจังหวัดตรงตัวตาม `/stations`)
- **สรุปทุกเช้า 07:00 (เวลาไทย) ทาง LINE** — ส่งให้ผู้สมัครที่ยังไม่ได้ปิด โดยใช้จังหวัดของสถานีที่ใกล้ตำแหน่งที่ส่งมา ระบบส่งวันละครั้งต่อคนในช่วง 07:00–10:59 (ตัวตั้งเวลา GitHub อาจช้าได้ จึงเผื่อช่วง ถ้าส่งไม่สำเร็จจะลองใหม่รอบถัดไป) ถ้าต้องการถี่ขึ้น ตั้ง env `DIGEST_EVERY_H` (เช่น 3 = 07:00, 10:00, 13:00, 16:00, 19:00 ไม่ส่งตั้งแต่ 22:00 กลุ่มแชตได้เฉพาะรอบ 07:00) ลองส่งทันทีด้วย `python notify.py digest` (ส่งได้เฉพาะในช่วงรอบสรุป)
- **บรรทัดเตือนฝนหนักในสรุปเช้า:** ถ้าพยากรณ์ฝน 24 ชม. ข้างหน้าของจังหวัดตั้งแต่ 35 มม. ขึ้นไป (ปรับด้วย env `RAIN_ALERT_MM`) สรุป 07:00 จะมีบรรทัด "🌧 พยากรณ์ฝน…" ต่อท้าย (`rainalert.py`) เรียก Open-Meteo ครั้งเดียวต่อจังหวัดที่มีผู้ติดตาม ใช้จุดกลางของสถานีในจังหวัด **ไม่ส่งตำแหน่งผู้ใช้ไปที่ไหน** ถ้าดึงพยากรณ์ไม่ได้ สรุปส่งตามปกติโดยไม่มีบรรทัดนี้ ไม่เพิ่มจำนวนข้อความ
- คำสั่งในแชต LINE: `รายงาน` ดูสรุปจังหวัดตอนนี้ · `ปิดสรุป` / `เปิดสรุป` · `สถานะ` · `ยกเลิก`
- ลิงก์ในข้อความใช้โดเมนจาก `VERCEL_PROJECT_PRODUCTION_URL` (Vercel ใส่ให้เอง) หรือกำหนดเองด้วย `PUBLIC_URL`
- **โควตาข้อความ LINE:** สรุปทุกเช้า = 1 ข้อความ/คน/วัน (~30/เดือน) รวมกับแจ้งเตือนเมื่อสถานะเปลี่ยน ถ้าตั้ง `DIGEST_EVERY_H=3` จะเป็น 5 ข้อความ/คน/วัน (~150/เดือน) ซึ่งอาจเกินเพดานของแผน LINE OA ตรวจเพดานข้อความของแผนที่ใช้ แล้วตั้ง `MAX_SUBSCRIBERS` ให้เหมาะสม
- กราฟย้อนหลังใช้ข้อมูลที่เก็บไว้ 31 วัน (วันที่ระบบยังไม่เคยเก็บจะว่างไว้) การเทียบกับเมื่อวานต้องมีประวัติครบ 24 ชม.

## แจ้งเตือนผู้ดูแลเมื่อดึงข้อมูลไม่ได้

ทุกรอบของ `/api/cron/ingest` ระบบตรวจ 2 อย่างแล้วส่ง LINE หาผู้ดูแล: (1) ดึงข้อมูลไม่สำเร็จต่อเนื่องเกิน 60 นาที (2) ดึงสำเร็จแต่ไม่มีสถานีไหนอัปเดตเกิน 6 ชั่วโมง ส่งครั้งแรกทันที เตือนซ้ำทุก 6 ชั่วโมงถ้ายังไม่หาย และแจ้งอีกครั้งเมื่อกลับมาปกติ (`watchdog.py`)

ระบบตรวจขนาดฐานข้อมูลทุกรอบด้วย ถ้าใช้เกิน 80% ของแพ็กเกจ จะส่ง LINE เตือนวันละครั้งจนกว่าจะลดลง (`watchdog.check_storage`) ตั้งขนาดแพ็กเกจด้วย env `DB_LIMIT_MB` (ค่าเริ่มต้น 512 = Neon ฟรี) โควตาการเรียกฟังก์ชันของ Vercel แอปอ่านเองไม่ได้ ให้ดูที่หน้า Usage ของ Vercel

**โควตาข้อความ LINE:** ทุก 6 ชม. ระบบถาม LINE เองว่าเดือนนี้ใช้ข้อความไปเท่าไรจากโควตา (`/v2/bot/message/quota`) ถ้าใช้เกิน 80% ส่งเตือนผู้ดูแลวันละครั้ง ถ้าแพ็กเกจไม่จำกัดจะไม่เตือน (`watchdog.check_line_quota`)

**กลุ่มสถานีที่เงียบพร้อมกัน:** เตือนผู้ดูแลเมื่อสถานีของหน่วยงานหนึ่งในจังหวัดหนึ่ง (อย่างน้อย 3 แห่ง) ไม่มีข้อมูลใหม่เกิน 6 ชม. ทั้งหมด หรือเมื่อหน่วยงานหนึ่งเงียบเกิน 25% ของสถานีทั้งหมด ขณะที่ส่วนอื่นยังปกติ แจ้งครั้งเดียวและแจ้งอีกครั้งเมื่อกลับมา (`watchdog.check_silent`) ตั้ง env `WATCH_PROVINCES=พระนครศรีอยุธยา,ปทุมธานี` (คั่นด้วยจุลภาค) เพื่อให้แจ้งเฉพาะจังหวัดของคุณ จังหวัดอื่นเงียบไม่ส่ง และสัดส่วนของหน่วยงานนับเฉพาะในจังหวัดเหล่านั้น ไม่ตั้ง = ทั่วประเทศ (ค่า `silent_groups` ใน `/api/cron/stats` ถูกกรองด้วย) ถ้าทั้งระบบดึงข้อมูลไม่ได้ ตัวตรวจเดิมจะแจ้งแทน

**สถิติการส่งข้อความ:** ตาราง `send_log` เก็บ 60 วัน แต่ละแถวมีแค่เวลา ประเภท (status/early/fast/report/digest และ admin = ข้อความเตือนเจ้าของระบบจาก watchdog ซึ่งกินโควตา LINE เหมือนกัน) จังหวัด และส่งสำเร็จหรือไม่ ไม่มี LINE ID ดูได้ที่ `GET /api/cron/stats?days=7` ด้วยรหัสเดียวกับ cron (`Authorization: Bearer ...`) ได้จำนวนต่อวัน ต่อประเภท ต่อจังหวัด จำนวนผู้ติดตาม ขนาดฐานข้อมูล โควตา LINE และกลุ่มสถานีที่เงียบ

**ทดสอบเกณฑ์เตือนน้ำขึ้นเร็วย้อนหลัง:** `python backtest_fast.py --db water.db` (หรือ `--api https://เว็บของคุณ --days 30` ซึ่งอ่านจาก API ของเราเอง ช้าเพราะเรียกทีละสถานี) จำลองว่ามีคนอยู่ติดสถานีละคน นับจำนวนข้อความที่จะถูกส่ง แยกส่วนที่เตือนล่วงหน้าเดิมส่งอยู่แล้ว ใช้ปรับ `FAST_RISE_M` / `FAST_MIN_PCT` ใน `notify.py` ไม่ส่งอะไรและไม่แก้ข้อมูล

**จำกัดการเรียกซ้ำ:** `ratelimit.py` จำกัดผู้เยี่ยมชมแต่ละรายไม่เกิน 240 ครั้งต่อนาทีที่ API (`/api/*`, `/stations*`, `/reports*`) เกินแล้วได้ 429 พร้อม `Retry-After` ตั้งเองด้วย env `RATE_LIMIT_PER_MIN` (0 = ปิด) ข้อจำกัด: บน Vercel แต่ละ instance มีหน่วยความจำของตัวเอง จึงเป็นการกันแบบ best-effort ไม่ใช่เพดานรวมที่เด็ดขาด ส่วนหนึ่งของภาระถูกดูดซับด้วยแคชของ CDN อยู่แล้ว ผู้ที่ใช้ Wi-Fi เดียวกันหลายคนใช้ที่อยู่เดียวกัน ถ้าถูกบล็อกบ่อยให้เพิ่มค่านี้ ไม่นับ `/health`, `/api/cron/*` และ `/api/line/webhook`

**สำรองข้อมูลผู้ติดตาม:** รายชื่อผู้ติดตาม LINE อยู่ในฐานข้อมูลที่เดียว รัน `DATABASE_URL="..." python backup_export.py` บนเครื่องของคุณ (สตริงเชื่อมต่อ Neon อยู่ใน Environment Variables ของโปรเจกต์ Vercel) ได้ไฟล์ `backup-วันที่.json` ที่เปิดอ่านได้เฉพาะคุณ ไม่อัปโหลดไปไหน และไม่พิมพ์ LINE ID ขึ้นจอ เก็บเป็นความลับและห้ามใส่ใน repo (`.gitignore` กันไว้แล้ว) กู้คืนด้วย `python backup_export.py --restore ไฟล์.json` ซึ่งเพิ่มเฉพาะรายที่ยังไม่มี รันซ้ำได้ ไม่ซ้ำซ้อน ระบบส่ง LINE เตือนผู้ดูแลทุก 30 วันให้ทำสำรอง (เริ่มนับ 30 วันหลังรอบแรกที่ระบบทำงาน) ปิดได้ด้วย `BACKUP_REMIND=0` ไม่สำรองข้อมูลระดับน้ำ เพราะเติมกลับจาก ThaiWater ได้ภายในวัน

**โครงสร้างหน้าเว็บ:** `public/index.html` เหลือเฉพาะโครงหน้ากับสคริปต์เล็กๆ ที่ต้องทำงานก่อน (เริ่มดึง `/stations` ทันที ซ่อนเบอร์ฉุกเฉินชั่วครู่ระหว่างโหลด) ส่วน CSS อยู่ที่ `public/app.css` และ JavaScript ที่ `public/app.js` ซึ่งเบราว์เซอร์แคชแยกกันได้ **กติกาเวลาแก้ไฟล์เหล่านี้:** ต้องเพิ่มเลขเวอร์ชันพร้อมกันสามที่ คือ `?v=` ของ `app.css` และ `app.js` ใน `index.html` และ `SHELL = "nkb-shell-vNN"` กับรายการไฟล์ใน `public/sw.js` มีเทสต์ (`test_pages.py`) ตรวจว่าตรงกัน ถ้าลืม เบราว์เซอร์ของผู้ใช้อาจค้างไฟล์เก่า

**เปิดซ้ำเร็ว:** service worker เปิดหน้าจากแคชทันทีแล้วอัปเดตเบื้องหลัง (ผลคือหลังอัปโหลดเวอร์ชันใหม่ ผู้ใช้จะเห็นเวอร์ชันใหม่ในการเปิดครั้งถัดไป ไม่ใช่ทันที) ส่วนข้อมูลสถานีไม่ผ่านแคชของ service worker แต่หน้าเว็บเก็บรายการสถานีล่าสุดที่โหลดสำเร็จไว้ในเครื่อง (Cache API ชื่อ `nkb-data`) ถ้าเน็ตช้าหรือหลุด จะแสดงชุดที่บันทึกไว้ก่อนพร้อมแถบบอกอายุ ("บันทึกเมื่อ 14:05 น. (45 นาทีก่อน)") ไม่เก่ากว่า 12 ชั่วโมง และแทนที่ด้วยข้อมูลใหม่ทันทีที่มา ถ้าเปิดครั้งแรกและเชื่อมต่อไม่ได้เลย ยังขึ้นแถบข้อผิดพลาดตามเดิม การเปิดแบบออฟไลน์เต็มรูปแบบ (ไลบรารีแผนที่จาก cdnjs) ยังไม่รองรับ

**เทสต์หน้าเว็บด้วยเบราว์เซอร์:** โฟลเดอร์ `e2e/` เปิดหน้าจริงใน Chromium บน API ที่ใช้ฐานข้อมูลทดสอบ แล้วตรวจพฤติกรรม (เรียงรายการ เทียบกราฟ กล่องศูนย์พักพิงและเบอร์โทร โหมดแบตต่ำ สีเส้นขอบ เบอร์ฉุกเฉินที่ต้องขึ้นเสมอ การแสดงข้อมูลที่บันทึกไว้ตอนเน็ตช้า/หลุด ฯลฯ) และจะล้มเหลวถ้าหน้าเว็บมี JavaScript error หรือถูก CSP บล็อก ไม่รวมใน `pytest` ปกติ รันเองด้วย `pip install playwright && playwright install chromium` แล้ว `E2E=1 python -m pytest e2e -q` (เพิ่ม `E2E_CHROME=1` เพื่อใช้ Chrome ในเครื่อง) ต้องต่ออินเทอร์เน็ต เพราะไลบรารีแผนที่มาจาก cdnjs GitHub รันให้อัตโนมัติด้วย `.github/workflows/e2e.yml`

**ล็อกไลบรารีแผนที่ด้วย SRI:** แท็ก `<script>`/`<link>` ของ Leaflet และ MarkerCluster จาก cdnjs ใน `index.html` มี `integrity="sha384-..."` ถ้าไฟล์ที่ cdnjs ส่งมาไม่ตรงกับค่านี้ (เช่น ถูกเจาะหรือถูกแก้) เบราว์เซอร์จะไม่รันไฟล์นั้น หน้าเว็บจะไม่มีแผนที่ แต่เบอร์ฉุกเฉินยังขึ้นเสมอ (มีเทสต์ที่จำลองการแก้ไฟล์) ถ้าจะอัปเกรดเวอร์ชันไลบรารี ต้องคำนวณค่าใหม่: `curl -s URL | openssl dgst -sha384 -binary | openssl base64 -A` แล้วใส่หลัง `sha384-` มีเทสต์ตรวจว่าทุกแท็กมีค่านี้ ส่วน Google Fonts ใส่ SRI ไม่ได้ เพราะเนื้อหาเปลี่ยนตามเบราว์เซอร์

**ความต่างสี (WCAG AA):** `e2e/contrast.py` วัดความต่างสีของข้อความทุกชิ้นที่เห็นบนหน้าจริงจากสีที่เบราว์เซอร์คำนวณแล้ว (4.5:1 สำหรับข้อความทั่วไป 3:1 สำหรับตัวใหญ่) และ `e2e/test_contrast.py` ตรวจทุกหน้าจอ (แผนที่ การ์ดสถานี ชั้นแผนที่ กล่องรายงาน/เส้นทาง ค้นหา หน้าคู่มือ/ความเป็นส่วนตัว/รายงาน) ทั้งโหมดสว่าง/มืด บนจอมือถือ/จอใหญ่ สีข้อความสถานะใช้ตัวแปร `--alert-ink` ฯลฯ (เข้มกว่าสีเติมของหมุด) ถ้าเพิ่มสีใหม่แล้วอ่านยาก เทสต์จะล้มพร้อมบอกองค์ประกอบ สีและอัตราส่วน ข้อจำกัด: ข้ามส่วนที่พื้นหลังเป็นรูปหรือไล่สี และไม่วัดสีของข้อความที่วางบนไทล์แผนที่โดยตรง

**ฝนที่เครื่องวัดจริง:** `gauges.py` ดึงฟีด `rain_24h` ของ ThaiWater (ราว 4,600 สถานี ฝนสะสม 24 ชม. และ 1 ชม.) แคช 10 นาทีต่อ instance (ฟีดใหญ่ราว 4.6 MB บีบอัดแล้ว 0.6 MB) ไม่นับค่าที่เก่ากว่า 3 ชม. `GET /api/rain?province=...` ได้สรุปรายจังหวัด หรือ `?lat=&lng=` ได้เครื่องวัดที่ใกล้ที่สุดในรัศมี 25 กม. แสดงในการ์ดฝนข้างพยากรณ์ (ซึ่งมาจากแบบจำลอง) และเป็นบรรทัดในสรุป LINE เมื่อจังหวัดมีเครื่องวัดที่วัดได้ตั้งแต่ `RAIN_ALERT_MM` (ค่าเริ่มต้น 35 มม.) ขึ้นไป

**ความสูงของพื้นที่เทียบระดับน้ำ:** เมื่อผู้ใช้กด "ตำแหน่งฉัน" หรือปักหมุดบ้าน เบราว์เซอร์ถาม Open-Meteo Elevation (แผนที่ความสูงละเอียดราว 90 ม.) แล้วแสดงตัวเลขความสูงเทียบระดับน้ำปัจจุบันของสถานีที่ใกล้ที่สุด (ห่างไม่เกิน 15 กม. และข้อมูลไม่ค้าง) เป็นการเทียบตัวเลขอย่างหยาบ ไม่รวมความลาดของแม่น้ำ คันกั้นน้ำ หรือน้ำที่ขังในพื้นที่ จึงเขียนกำกับไว้ชัดว่าไม่ได้บอกว่าจะท่วมหรือไม่ท่วม และไม่ใช้คำว่าปลอดภัย **ถ้าสถานีที่ใกล้ที่สุดอยู่ระดับเฝ้าระวังหรือเตือนภัย หรือระดับน้ำตั้งแต่ 50% ของตลิ่งขึ้นไป จะแสดงเฉพาะความสูงของพื้นที่ ไม่เปรียบเทียบกับระดับน้ำเลย** (เพื่อไม่ให้ประโยค "สูงกว่าน้ำ" ทำให้คนสบายใจเกินจริงตอนน้ำใกล้ตลิ่ง) มีเทสต์ตรวจ

**ลองแล้วไม่ใช้: Open-Meteo Flood API (ปริมาณน้ำในแม่น้ำ)** ทดสอบเทียบกับสถานีของ ThaiWater ที่มีค่าอัตราการไหลจริง 12 แห่ง ได้ค่าต่างกันมาก เช่น C.2 นครสวรรค์ สถานีวัดได้ 2,572 ลบ.ม./วินาที แต่ API ให้ 1.9 และ C.3 บางพุทรา 2,424 เทียบกับ 25.7 ส่วนที่แม่น้ำสายเล็กต่างกัน 3–10 เท่าทั้งสูงและต่ำกว่า (มีแค่แม่น้ำมูลที่ใกล้เคียงกัน) แบบจำลองระดับโลกความละเอียดราว 5 กม. จับแม่น้ำสายหลักของไทยไม่ถูก จึงไม่นำมาแสดง ถ้าจะลองใหม่ ให้เทียบกับค่าสถานีก่อนเสมอ

**ตรวจเว็บจริงอัตโนมัติ:** `.github/workflows/smoke.yml` รอให้ Vercel deploy เสร็จหลังทุกครั้งที่อัปโหลด (และรันซ้ำวันละ 4 ครั้ง) แล้วเปิดหน้าเว็บจริงด้วยเบราว์เซอร์ ตรวจว่าแผนที่กับสรุปขึ้น ไม่มี JavaScript error หรือ CSP บล็อก `/health` ปกติ ถ้าพังงานจะล้มเหลวและ GitHub ส่งอีเมลหาเจ้าของ สคริปต์คือ `smoke_check.py` ลองรันเองได้ด้วย `pip install playwright` แล้ว `SMOKE_CHROME=1 python smoke_check.py` (ใช้ Chrome ในเครื่อง)

**น้ำขึ้นเร็ว:** `core.fast_risers` จัดอันดับสถานีที่ระดับน้ำ (เมตร) เพิ่มตั้งแต่ 0.30 ม. ใน 3 ชม. แม้ยังต่ำกว่าเกณฑ์เตือน ค่าที่กระโดดเกิน 2 ม. ระหว่างสองการอ่าน หรือเกิน 3 ม. รวมใน 3 ชม. ถือเป็นเซ็นเซอร์ผิดปกติและไม่นับ แสดงในการ์ดสถานการณ์บนเว็บ (`rise_3h_m` ใน `/stations`) และเป็นบรรทัด "น้ำขึ้นเร็วใน 3 ชม." ในสรุป LINE

**น้ำขึ้นน้ำลงของทะเล:** สถานีใกล้ชายฝั่ง (เช่น สมุทรปราการ สมุทรสงคราม สมุทรสาคร ตรัง ตราด พุนพิน) ระดับน้ำขึ้นลง 1.6–2.4 ม. ทุกวันตามน้ำทะเลหนุน ไม่ใช่น้ำหลาก `core.is_tidal` ดูย้อนหลัง 72 ชม. ถ้ามีจุดกลับทิศ (สวิงอย่างน้อย 0.4 ม.) ห่างกัน 4–14 ชม. ตั้งแต่ 3 ช่วงขึ้นไป ถือว่าเป็นน้ำขึ้นน้ำลง `core.mark_tidal` จึงตั้ง `rise_3h_m` เป็นว่างและ `rise_tidal` เป็นจริง (ไม่ขึ้นในรายการน้ำขึ้นเร็ว ไม่ส่งเตือนน้ำขึ้นเร็ว) เช็คเฉพาะสถานีที่ขึ้นเกิน 0.30 ม. ด้วยคำสั่งเดียว ไม่กระทบความเร็ว `/stations` ทดสอบกับข้อมูลจริง 10 วัน: สถานีชายฝั่งถูกจัดเป็นน้ำขึ้นน้ำลง 5 จาก 7 เหตุการณ์ และสถานีในแผ่นดินถูกจัด 6 จาก 34 (ล้วนเป็นสถานีปากแม่น้ำ เช่น พุนพิน เมืองตรัง เมืองตราด) ข้อจำกัด: สถานีปากแม่น้ำที่น้ำหลากจริงจะไม่ได้รับเตือน "น้ำขึ้นเร็ว" (ยังได้เตือนตามสถานะและเวลาถึงตลิ่งตามปกติ)

**งบข้อความ LINE:** `budget.py` ถามโควตาจาก LINE (ไม่เกินทุก 30 นาที เก็บคำตอบใน `alert_state`) เมื่อเหลือไม่เกินส่วนสำรอง (5% ของเพดานต่อเดือน อย่างน้อย 10 ข้อความ ปรับด้วย env `MSG_RESERVE_PCT`) ระบบจะส่งเฉพาะข่าวระดับเตือนภัยกับข้อความถึงเจ้าของ ส่วนอย่างอื่นรอ: สถานะที่เปลี่ยนเป็นปกติ/เฝ้าระวังค้างไว้ส่งทีหลังถ้ายังต่างอยู่ (เหมือนช่วงไม่รบกวนกลางคืน) สรุปเช้ารอรอบถัดไปของช่วงเวลาเดิม เตือนน้ำขึ้นเร็วและรายงานน้ำท่วมใกล้บ้านไม่ส่ง การตอบที่ผู้ใช้พิมพ์หาบอตไม่นับโควตา ไม่ถูกกระทบ ถ้าถาม LINE ไม่ได้หรือแผนไม่จำกัด จะไม่พักอะไรเลย (ไม่รู้ ไม่ใช่เหตุให้เงียบ) ข้อจำกัด: ตัวเลขของ LINE อัปเดตช้ากว่าการส่งจริงเล็กน้อย ระบบจึงนับข้อความที่ส่งในรอบเองเพิ่มด้วย

**สูงกว่าตลิ่งกี่ ซม.:** `core.over_bank_cm` = (ระดับน้ำ − ระดับตลิ่ง) × 100 ปัดทีละ 5 ซม. ฟิลด์ `over_bank_cm` ใน `/stations` ส่งเมื่อข้อมูลไม่ค้าง มีทั้งสองค่า อยู่ในช่วง −100 ถึง +300 ซม. (เกิน +300 ถือว่าน่าจะเป็นความคลาดของ datum ต้นทาง ไม่แสดง) และไม่ขัดกับ % ของตลิ่ง (ซึ่งวัดจากท้องน้ำ: ถ้า % ≥ 100 แต่ซม. ติดลบ หรือกลับกัน แปลว่าตัวเลขสามค่าไม่สอดคล้องกัน ไม่แสดง) แสดงใต้ % ในการ์ดสถานี ภาพแชร์ (แทนบรรทัดระดับน้ำดิบ) การ์ดและข้อความ LINE พร้อมคำกำกับว่าเป็นค่าประมาณจากตลิ่งต่ำสุดของสถานี ไม่ใช่ความลึกน้ำที่บ้าน `core.over_bank_text` สร้างข้อความ ตัวเลข 300 และ 100 เป็นเกณฑ์ที่ผมตั้งเอง ไม่ได้มาจากหน่วยงาน

**ซม.เหนือตลิ่งในรายการ หมุด และกราฟ (เว็บ):** ค่า `over_bank_cm` เดียวกันแสดงต่อท้ายแถวในรายการสถานี ("น้ำสูงสุด" / ใกล้ฉัน / ผลค้นหา) และใน title ของหมุดแผนที่ (ตัวเลขบนหมุดยังเป็น % ตามคำอธิบายสัญลักษณ์) กราฟย้อนหลัง 7 วันมีแกนขวาเป็น ซม. เทียบตลิ่ง (0 = ตลิ่ง) คำนวณจากสัดส่วน (ตลิ่ง − ท้องน้ำ) ต่อ 1% จึงต้องมีทั้งสองค่า และใต้กราฟบอกค่าสูงสุดใน 7 วันเมื่อน้ำเกินตลิ่ง `cmOf` ใน app.js ใช้เกณฑ์และการตรวจความสอดคล้องเดียวกับ `core.over_bank_cm` (ต้องแก้สองที่ให้ตรงกัน) ข้อจำกัด: ค่าในกราฟคำนวณซ้ำฝั่งเบราว์เซอร์จากระดับน้ำย้อนหลังกับตลิ่งปัจจุบันของสถานี ถ้าต้นทางแก้ค่าตลิ่งภายหลัง กราฟจะเปลี่ยนตาม

**แผนที่ที่ไม่มีขนาด:** ถ้ากรอบแผนที่มีขนาดเป็นศูนย์ (แท็บพื้นหลัง เลย์เอาต์ที่ยุบ) Leaflet คำนวณซูมไม่ได้และไม่รู้ว่ากรอบกลับมา `fitMap()` ใน app.js จึงเลื่อนการ fit ไว้จนกรอบมีขนาด และ ResizeObserver เรียก `invalidateSize` ทุกครั้งที่กรอบเปลี่ยนขนาด (ไม่เลื่อนมุมมอง) มีเทสต์ e2e ทั้งกรณีสูญเสียขนาดกลางทางและกรณีเริ่มต้นโดยไม่มีขนาด

**ความปลอดภัยที่ปิดไว้ตามค่าตั้งต้น (ผลสแกน 6 ต.ค.):** (1) `/api/ews/warnings` ตอบ 404 เว้นแต่ตั้ง `EWS_ENABLED=1` (เว็บไม่ใช้ DWR ไม่ตอบจากนอกไทย คำขอหนึ่งครั้งค้างราว 15 วินาที และใครก็เรียกวนเพื่อเผาเวลาฟังก์ชันได้) และเมื่อพังตอบแค่ "unavailable" รายละเอียดไปที่ log (2) พร็อกซีภาพ GISTDA ตอบเฉพาะ tile ที่ทับกรอบประเทศไทย (lat 5.4–20.7, lng 97.2–105.8) ที่ซูม 5–15 `api.tile_in_thailand` ไม่งั้น 404 ไม่เรียก GISTDA กันใช้โควตา API key ฟรีเปลืองหรือยิงเลข tile วนข้ามแคช (3) `/docs` `/redoc` `/openapi.json` ปิด เปิดได้ด้วย `ENABLE_DOCS=1` ตอนพัฒนา (4) `x-forwarded-for` เชื่อเฉพาะบน Vercel (ตัวแปร `VERCEL`) หรือเมื่อตั้ง `TRUST_PROXY=1` ถ้ารัน Docker หลัง reverse proxy ที่เขียนหัวนี้ทับให้ ต้องตั้ง `TRUST_PROXY=1` เอง ไม่งั้นทุกคนถูกนับเป็นที่อยู่ของ proxy ตัวเดียว (5) ทุก workflow ตั้ง `permissions` แบบอ่านอย่างเดียว มีเทสต์ตรวจ รอบสอง: (6) CSP ไม่มี `'unsafe-inline'` ใน `script-src` แล้ว: อนุญาตเฉพาะไฟล์ของเราเอง cdnjs และสคริปต์ inline ของหน้า 4 ก้อนที่ระบุด้วยแฮช SHA-256 (`INLINE_SCRIPT_HASHES` ใน `security.py` กับ `script-src` ใน `vercel.json`) `<script>` ที่ถูกแทรกหรือ `onclick=` จึงไม่ทำงาน `test_security.py` คำนวณแฮชจาก `public/*.html` ซ้ำ ถ้าแก้สคริปต์ inline แล้วลืมอัปเดต เทสต์ล้มและพิมพ์ค่าที่ต้องใส่ให้ และห้ามมี `onclick=` หรือ `javascript:` ในหน้า (ปุ่ม "พิมพ์" ในรายงานจึงเปลี่ยนเป็น addEventListener) มีเทสต์ e2e ที่ลองแทรกสคริปต์และ handler แล้วดูว่าเบราว์เซอร์บล็อก `style-src` ยังมี `'unsafe-inline'` เพราะหน้าใช้ `style=""` อยู่มาก (7) CORS อนุญาตเฉพาะ GET จากทุกที่ และ POST ของรายงานน้ำท่วม (`/api/flood-reports*`) ถ้ามีหัว `Origin` ต้องมาจากโฮสต์ของเราเอง ไม่งั้น 403 สคริปต์และเครื่องมือที่ไม่ส่ง Origin ยังใช้ได้ (8) `public/robots.txt` กัน `/admin.html` และ `/api/` ออกจากเสิร์ช ที่ยังไม่ทำ: ตรึงเวอร์ชันไลบรารี (ต้องตรวจว่า Vercel ติดตั้งเวอร์ชันที่ตรึงได้ก่อน)

**ตรึงเวอร์ชันไลบรารี:** `requirements.txt` และ `dependencies` ใน `pyproject.toml` (Vercel ติดตั้งจากไฟล์หลัง) ระบุเวอร์ชันเป๊ะ (`==`) ของทุกอย่างที่แอปรันจริง รวมไลบรารีที่ถูกดึงตามมา ไม่ให้ deploy ครั้งหน้าได้ไลบรารีรุ่นใหม่ที่ไม่มีใครเคยรัน (สองไฟล์ต้องเหมือนกันทุกบรรทัด) มี 2 ชุดเพราะรุ่นล่าสุดต้องใช้ Python 3.10 ขึ้นไป: `python_version >= "3.10"` คือชุดที่ production รันอยู่ (fastapi 0.142.2, starlette 1.7.0, uvicorn 0.54.0, psycopg 3.3.6 บน Python 3.12 ของ Vercel/Docker และ 3.11 ของงาน e2e/smoke) กับ `python_version < "3.10"` คือรุ่นใหม่สุดที่ยังรองรับ 3.9 (ใน `.venv` ในเครื่องและงาน tests) ชุด 3.12 ผมตรวจแล้วว่ามี wheel ครบสำหรับ Linux/cp312 ดึงมาได้โดยไม่ขัดกัน (ไม่ได้รันแอปด้วย Python 3.12 ในเครื่อง เพราะเครื่องนี้ไม่มี) ผลการทดสอบของชุด 3.12 ดูจากงาน e2e/smoke บน GitHub และเว็บจริงที่รันรุ่นเหล่านี้อยู่แล้ว เทสต์ใน `test_pages.py` บังคับว่าทุกบรรทัดเป็น `==` ว่าสองไฟล์ตรงกัน และว่า `.venv` ติดตั้งตรงกับชุด 3.9 วิธีอัปเดต: เปลี่ยนสองชุดพร้อมกัน รันเทสต์กับ e2e แล้ว `audit` จะรันเองเมื่อสองไฟล์นี้เปลี่ยน (และทุกวันที่ 5) ข้อแลกเปลี่ยน: เวอร์ชันที่ตรึงไว้จะไม่ได้แพตช์ความปลอดภัยเองอีก ต้องรอ `audit` เตือนแล้วอัปเดตเอง

**รวมแจ้งเตือนหลายจุดเป็นข้อความเดียว:** คนที่บันทึกไว้หลายจุด (สูงสุด 3) แล้วหลายจุดมีเรื่องต้องแจ้งในรอบเดียวกัน (สถานะเปลี่ยน เตือนล่วงหน้า น้ำขึ้นเร็ว หรือรายงานน้ำท่วมใกล้บ้าน) จะได้ข้อความเดียว: ข้อความธรรมดามีหัว "มีการเปลี่ยนแปลง N จุด" รายละเอียดแต่ละจุด และคำเตือนท้ายครั้งเดียว กับการ์ดแบบ carousel อันเดียว (LINE นับโควตาตามจำนวน message object ไม่ใช่จำนวนการ์ด จึงนับ 1 ข้อความ) ข่าวที่ไม่มีการ์ดของตัวเอง (รายงานน้ำท่วมจากผู้ใช้) ได้การ์ดเล็กในชุดเดียวกัน แจ้งจุดเดียวยังเหมือนเดิมทุกอย่าง งบข้อความและ send_log นับเป็น 1 ข้อความ (บันทึกเป็นประเภทที่ร้ายแรงสุดของชุด) ถ้าส่งไม่สำเร็จ ทุกจุดในชุดไม่ถูกทำเครื่องหมายว่าแจ้งแล้ว และจะส่งใหม่รอบถัดไป ถ้า LINE ปฏิเสธการ์ด ระบบส่งข้อความธรรมดาแทนเหมือนเดิม ข้อจำกัด: ผมไม่ได้ลองส่ง carousel กับ LINE จริง (ทดสอบเฉพาะโครงสร้างกับของปลอม)

**หน้าหลังบ้าน (`/admin.html`):** หน้าอ่านอย่างเดียวสำหรับเจ้าของ ใส่รหัส cron (`CRON_SECRET` หรือ `CRON_SECRET_EXTERNAL`) ในช่องของหน้านั้น รหัสอยู่ใน `sessionStorage` ของแท็บเท่านั้น (ปิดแท็บหรือกด "ออก" แล้วหาย ไม่ลง localStorage ไม่อยู่ใน URL) แสดงสถานะการดึงข้อมูล โควตา LINE (เหลือเท่าไร กำลังพักข้อความไม่เร่งด่วนหรือไม่) ฐานข้อมูลและผู้ติดตาม สถานีที่เงียบ ข้อความที่ส่งแยกวันและประเภท จังหวัดที่ได้รับมากสุด และเวลาเตือนสำรองข้อมูลครั้งถัดไป ข้อมูลมาจาก `/api/cron/stats` (เพิ่มฟิลด์ `budget`, `backup`, `watch_provinces`) หน้าเป็นไฟล์นิ่ง ไม่มีข้อมูลอยู่ในตัวหน้า มี `noindex` ไม่ลิงก์จากหน้าสาธารณะ และมีเทสต์ e2e (`e2e/test_admin.py`) รวมสีตัวอักษร

**ตรวจช่องโหว่ไลบรารีรายเดือน:** `.github/workflows/audit.yml` รัน `pip-audit -r requirements.txt` วันที่ 5 ของทุกเดือน (กดรันเองได้ที่ Actions → audit → Run workflow) ถ้าไลบรารีที่ใช้งานจริงมีช่องโหว่ที่รู้จัก งานจะล้มเหลวและ GitHub ส่งอีเมลหาเจ้าของ ตรวจเฉพาะ `requirements.txt` ไม่รวมเครื่องมือทดสอบ

**ลิงก์แชร์จุด (เว็บ):** การ์ด "สถานีที่ใกล้ที่สุด" ของบ้าน/ตำแหน่งปัจจุบัน/พื้นที่ที่เลือก มีปุ่ม "แชร์ลิงก์จุดนี้" สร้างลิงก์ `/?lat=13.912&lng=100.545` (ปัดเป็นทศนิยม 3 ตำแหน่ง ≈ 100 ม. ไม่ใส่ `station` หรือ `api` หรืออย่างอื่น) เปิดลิงก์แล้วหน้าจะตั้งจุดนั้นเป็นต้นทาง (ชนิด `shared` ป้าย "จุดที่แชร์" ไม่เรียกว่า "บ้านของคุณ") แสดงสถานีใกล้ ศูนย์พักพิง ฝนและความสูงพื้นที่เหมือนจุดที่ปักไว้ รับเฉพาะตัวเลขในประเทศไทย (lat 5–21, lng 97–106) ค่าอื่นถูกเมินทั้งลิงก์ ถ้าลิงก์มี `?station=` ด้วยจะเปิดสถานีนั้นก่อน ไม่มีการเก็บอะไรที่เซิร์ฟเวอร์ (หน้านโยบายความเป็นส่วนตัวบอกไว้แล้ว)

**ผู้ติดตามใหม่เริ่มแบบปิดสรุปเช้า:** ผู้ใช้ที่ส่งตำแหน่งครั้งแรกจะไม่ได้สรุปเช้าจนกว่าจะพิมพ์ "เปิดสรุป" (ประหยัดราว 30 ข้อความต่อคนต่อเดือน จากโควตาฟรี 300) ตั้ง env `NEW_USER_DIGEST=1` เพื่อกลับไปเป็นเปิดไว้ก่อนเหมือนเดิม ไม่กระทบคนที่สมัครไว้แล้ว และกลุ่ม LINE (ได้เฉพาะสรุป) ถ้าโควตาข้อความเดือนนี้ใกล้เต็ม (งบข้อความ) บอตบอกผู้สมัครใหม่และคนที่กด "เปิดสรุป" ว่าตอนนี้จะแจ้งเฉพาะระดับเตือนภัย

**เขื่อนใหญ่ (ThaiWater):** `dams.py` ดึงฟีด `analyst/dam` (ราว 170 KB บีบอัด 1 MB ดิบ เปลี่ยนวันละครั้ง จึงแคช 30 นาที) ใช้เฉพาะ `dam_daily` (ราว 50 เขื่อนใหญ่ ส่วน `dam_hourly` ในฟีดเป็นข้อมูลปี 2020 ไม่ใช้ และเขื่อนกลาง/เล็กมีมากเกินไปและเป็นเรื่องท้องถิ่น) ตัด `dam_date` เก่ากว่า 3 วัน เปอร์เซ็นต์คือสัดส่วนของ "ความจุเก็บกักปกติ" ตามที่ ThaiWater ให้มา เกิน 100% ได้ (เช่น ป่าสักฯ 110%) จังหวัดหนึ่งจับกับเขื่อนผ่าน **ลุ่มน้ำ** ของสถานีในจังหวัดนั้น (ลุ่มน้ำที่มีสถานีตั้งแต่ 2 แห่ง) บวกลุ่มน้ำต้นน้ำตามตาราง `UPSTREAM` (เจ้าพระยา ← ปิง วัง ยม น่าน สะแกกรัง ป่าสัก; มูล ← ชี) ตารางนี้เป็นความรู้ภูมิศาสตร์ทั่วไป ถ้าจะเพิ่มลุ่มน้ำให้ใส่เองตรงนั้น `GET /api/dams?province=&limit=` ให้เว็บใช้ แสดงเป็นการ์ดใต้การ์ดฝน (ชื่อเขื่อน % ที่เก็บ และการระบายล้าน ลบ.ม./วัน พร้อมข้อความว่าเป็นบริบท ไม่ได้บอกว่าจะท่วม) และสรุป LINE ของจังหวัดจะมีบรรทัด "🏞 เขื่อนใหญ่ในลุ่มน้ำนี้และต้นน้ำที่เก็บน้ำสูง" เมื่อมีเขื่อนตั้งแต่ `DAM_ALERT_PCT` (ค่าเริ่มต้น 90%) ไม่เพิ่มจำนวนข้อความ ถ้าดึงฟีดไม่ได้ ไม่มีการ์ดและไม่มีบรรทัด (ไม่ขึ้น error)

**ฝนสะสมย้อนหลัง 3 วัน (เว็บ):** การ์ดฝนขอ `past_days=3` จาก Open-Meteo แล้วบอก "ที่ผ่านมา 24 ชม. … · 3 วันรวม ~N มม." ถ้า ≥ 100 มม. (`RAIN72_HIGH` ใน `app.js`) เพิ่มประโยค "ฝนสะสม 3 วันค่อนข้างมาก ถ้าฝนตกซ้ำ น้ำอาจระบายช้าและท่วมขังได้ง่ายกว่าปกติ (ประมาณจากแบบจำลอง)" ไม่มีประโยคตรงข้าม (ฝนน้อยไม่ได้แปลว่าปลอดภัย) ตัวเลข 100 มม. เป็นเกณฑ์ที่ผมตั้งเองไม่ได้มาจากหน่วยงาน ปรับได้

**"แชร์ให้ญาติ" ใน LINE:** พิมพ์ "แชร์ให้ญาติ" (หรือ แชร์ / ชวนญาติ / แตะปุ่มในเมนู) ได้การ์ดที่มีปุ่ม "ส่งต่อ: <ชื่อจุด>" ต่อจุดที่บันทึก ปุ่มเปิดหน้าเลือกผู้รับของ LINE (`https://line.me/R/share?text=…`) พร้อมข้อความและลิงก์ `/?lat=…&lng=…` (พิกัดปัดราว 100 ม.) ผู้ใช้เลือกส่งเอง ระบบไม่ส่งลิงก์ให้ใคร ต้องตั้งที่อยู่เว็บ (`PUBLIC_URL` หรือ Vercel ใส่ให้) ถ้าไม่มี บอกให้ใช้ปุ่มแชร์บนเว็บแทน

**โหมดสี สว่าง/มืด:** เริ่มต้นตามเครื่อง (`prefers-color-scheme`) เลือกบังคับ "สว่าง" หรือ "มืด" ได้ในแผงชั้นแผนที่ (หัวข้อ "โหมดสี") เก็บค่าใน `localStorage` ชื่อ `nkb-theme` ค่าเดียว (ถ้าเลือก "ตามเครื่อง" จะลบ) สคริปต์เล็กๆ ใน `<head>` ของหน้าแผนที่และหน้า help/privacy/report อ่านค่านี้แล้วตั้ง `data-theme` บน `<html>` ก่อนวาดหน้า (ไม่กะพริบ) CSS ใช้ชุดตัวแปรสีเข้มสองทาง: ใน `@media (prefers-color-scheme:dark)` เมื่อไม่ได้เลือกสว่าง และเมื่อ `data-theme="dark"` สีแถบเบราว์เซอร์ (`theme-color`) และสีเส้นขอบจังหวัดเปลี่ยนตาม หน้า admin ตามเครื่องอย่างเดียว (ตั้งใจไม่ให้แตะ localStorage) มีเทสต์ e2e (`e2e/test_theme.py`) ทั้งการบังคับสองทิศทาง การจำค่า การกลับเป็นอัตโนมัติ และความต่างสีของโหมดที่บังคับ หน้านโยบายความเป็นส่วนตัวระบุไว้แล้ว

**ปุ่มโหมดสีที่แถบบน:** ไอคอนข้างปุ่มชั้นแผนที่ (ครึ่งวงกลม = ตามเครื่อง, พระอาทิตย์ = สว่าง, พระจันทร์ = มืด) แตะวนตามเครื่อง → สว่าง → มืด และแจ้งด้วย toast แผงชั้นแผนที่ยังมีปุ่ม 3 ตัวเลือกเหมือนเดิม ทั้งสองทางใช้ `setTheme()` เดียวกันและตรงกันเสมอ (มีเทสต์)

**แชร์เป็นภาพ:** ปุ่ม "แชร์เป็นภาพ" ในการ์ดสถานี วาดภาพ PNG 1080x1350 ด้วย canvas ในเบราว์เซอร์ (ชื่อสถานี จังหวัด สถานะ % ของตลิ่ง แถบระดับ แนวโน้ม น้ำขึ้นใน 3 ชม. เวลาข้อมูล ข้อความ "ไม่ใช่ประกาศทางการ ยึด ปภ. 1784" และลิงก์) สีคงที่แบบสว่างเสมอไม่ว่าเว็บอยู่โหมดไหน ถ้าเบราว์เซอร์รองรับ `navigator.canShare({files})` เปิดเมนูแชร์ของเครื่องพร้อมข้อความ ไม่รองรับก็ดาวน์โหลดไฟล์ ไม่ส่งอะไรไปเซิร์ฟเวอร์ ฟอนต์ IBM Plex Sans Thai ถ้าโหลดไม่ทัน 1.5 วินาทีใช้ฟอนต์ระบบ เทสต์: ขนาดภาพ ชนิดไฟล์ ชื่อไฟล์ ข้อความที่แนบ และเส้นทางดาวน์โหลด

**ติดตั้งบนหน้าจอหลัก (PWA):** หัวข้อ "ติดตั้งบนหน้าจอหลัก" ในแผงชั้นแผนที่ ขึ้นเฉพาะเมื่อเบราว์เซอร์เสนอให้ติดตั้ง (`beforeinstallprompt` เก็บไว้แล้วใช้ปุ่มของเรา ใช้ได้ครั้งเดียวต่อ prompt) หรือเป็น iPhone/iPad ที่ไม่มีเหตุการณ์นั้น (แสดงคำแนะนำสองขั้น "แชร์ → เพิ่มลงในหน้าจอโฮม") ไม่ขึ้นเมื่อเปิดจากแอปที่ติดตั้งแล้ว (`display-mode: standalone`) manifest มีไอคอน PNG 192/512 (any และ maskable) และ `apple-touch-icon.png` 180 (iOS ไม่ใช้ SVG) สร้างจาก `icon.svg` ข้อจำกัด: ผมทดสอบเหตุการณ์ด้วยตัวจำลอง ยังไม่ได้ลองติดตั้งบนมือถือจริง และ Chrome เป็นฝ่ายตัดสินใจว่าจะเสนอให้ติดตั้งเมื่อไร

**เขื่อน: การเปลี่ยนใน 7 วัน:** ฟีดเขื่อนรายวันไม่มีประวัติ แต่ ThaiWater มี `analyst/dam_yearly_graph?data_type=dam_storage&dam_id=&year=` ให้ปริมาตรน้ำรายวันทั้งปี (ราว 14 KB บีบอัด) เมื่อแสดงเขื่อน เซิร์ฟเวอร์ดึงชุดนี้ของเขื่อนที่แสดง (สูงสุด 6 แห่ง ขนานกัน แคช 6 ชม.) แล้วคำนวณ (ปริมาตรวันนี้ − ปริมาตร 7 วันก่อน) ÷ ความจุปกติ × 100 เป็น "จุด" ของเปอร์เซ็นต์ (`dams.change_7d` ใช้วันข้างเคียงถ้าขาดหนึ่งวัน อ่านปีก่อนหน้าด้วยช่วงต้นปี) ขึ้นเมื่อ ≥ 1 จุด ("▲ +13.3 จุดใน 7 วัน") ทั้งในการ์ดเว็บและบรรทัด LINE ถ้าดึงชุดนี้ไม่ได้ ก็ไม่แสดงตัวเลข (ไม่ error) ตัวอย่างจริงวันที่ทดสอบ: ป่าสักชลสิทธิ์ +13.3 จุดใน 7 วัน

**ฝนสะสม 3 วันจากเครื่องวัดจริง:** ThaiWater มีฟีด `provinces/rain3d` (ราว 3,500 เครื่อง 330 KB บีบอัด) ให้ฝนสะสม 3 วันที่ครบแล้ว (ไม่รวมวันนี้) ต่อเครื่อง `gauges.get3` แคช 3 ชม. ตัดช่วงที่จบเกิน 3 วัน `/api/rain?province=` เพิ่ม `three_day` (สูงสุด เฉลี่ย จำนวนสถานีตั้งแต่ 100 มม.) และ `/api/rain?lat=&lng=` เพิ่ม `mm3d` ต่อเครื่อง (จับคู่ด้วยรหัสสถานี ไม่ใช่ทุกเครื่องมีตัวเลขนี้) กับ `three_day_period` การ์ดแสดงใต้บรรทัดฝน 24 ชม. พร้อมช่วงวันที่ ถ้าฟีดนี้ล่ม ส่วนอื่นไม่กระทบ ไม่ต้องสะสมข้อมูลเอง ไม่ใช้พื้นที่ฐานข้อมูลเพิ่ม ส่วน "3 วันรวม" ในประโยคเตือนของการ์ดพยากรณ์ยังมาจากแบบจำลอง Open-Meteo

**LINE พิมพ์ชื่อสถานที่:** ข้อความที่ไม่ใช่คำสั่ง (อย่างน้อย 3 ตัวอักษร) ค้นด้วย `suggest.search` เดียวกับช่องค้นหาบนเว็บ (ตำบล อำเภอ จังหวัด สถานี ไม่รวมศูนย์พักพิง) เจอที่เดียวหรือชื่อตรงเป๊ะตอบการ์ดสถานีใกล้สุด จังหวัดตอบรายงานจังหวัด หลายที่ให้ปุ่มเลือกไม่เกิน 5 (postback `act=look` / `act=prov`) ไม่บันทึกอะไร

**พักแจ้งเตือน 6 ชม.:** ปุ่มท้ายการ์ดสถานี หรือพิมพ์ "พักแจ้งเตือน" / "เลิกพัก" เก็บเวลาสิ้นสุดใน `subscriptions.snooze_until` (ทุกจุดของคนนั้น) ระหว่างพักถือเหมือนช่วงไม่รบกวนกลางคืน: ระดับเตือนภัยยังส่ง สถานะที่เปลี่ยนค้างไว้ส่งหลังพักครบถ้ายังต่างอยู่ สรุปรายวันไม่ถูกพัก

หัวป้องกันความปลอดภัย (CSP, X-Frame-Options ฯลฯ) อยู่ใน `security.py` และมีสำเนาใน `vercel.json` โดยมีเทสต์ตรวจว่าตรงกัน ถ้าหน้าเว็บเรียกโฮสต์ภายนอกเพิ่ม ต้องเพิ่มใน `connect-src` ด้วย การเปิดหน้าเว็บด้วย `?api=` ที่ชี้ไปโฮสต์อื่นจะถูกบล็อก

ตั้งค่า: ส่งข้อความ `ไอดีของฉัน` ให้บอต แล้วนำค่าที่ได้ไปใส่ env `ADMIN_LINE_ID` ใน Vercel (ไม่ตั้ง = ไม่ส่งอะไร) ข้อจำกัด: ถ้าตัวตั้งเวลาหยุดเรียกทั้งหมด (เช่น GitHub ปิด schedule หลัง repo เงียบ 60 วัน) ระบบจะไม่มีรอบให้ตรวจ ให้ดูอีเมลแจ้ง workflow ล้มของ GitHub เป็นตัวสำรอง

## สถานีเตือนภัยน้ำป่า (DWR) — มี API แต่ปิดจากหน้าเว็บ

(ปิดตามค่าตั้งต้น ต้องตั้ง `EWS_ENABLED=1`) `GET /api/ews/warnings` (`ews.py`) ดึงสถานีเตือนภัยของกรมทรัพยากรน้ำ (`ews.dwr.go.th`) เก็บเฉพาะสถานีที่ DWR ตั้งสถานะ 1–3 แล้วแคช 10 นาที ใช้งานได้เมื่อเซิร์ฟเวอร์อยู่ในประเทศไทย แต่บน Vercel (สิงคโปร์) เชื่อมต่อ DWR ไม่ได้ (`Connection timed out` เพราะ DWR ไม่ตอบ IP ต่างประเทศ) และ DWR ไม่เปิด CORS ให้เบราว์เซอร์เรียกตรง จึงถอดชั้น "น้ำป่า" ออกจากแผนที่ ถ้ารันเองบนเซิร์ฟเวอร์ในไทย (เช่น Docker) endpoint นี้ใช้ได้ทันที และสามารถเพิ่มชั้นกลับได้ (ดู commit `ece652a`) ต้นทางตอบช้าราว 16 วินาทีต่อครั้ง และธงสถานะที่ค้างหลังเหตุการณ์ผ่านไปแล้วยังไม่รู้ความหมายชัดเจน จึงไม่ควรใช้ส่งแจ้งเตือน

## แผนที่
- **กดตรงไหนก็ได้บนแผนที่** เพื่อดู 3 สถานีที่ใกล้จุดนั้นที่สุด
- **ค้นหาสถานที่:** พิมพ์ชื่อตำบล/ตลาด/วัด แล้วกด Enter (ใช้ Nominatim ของ OpenStreetMap คำค้นจะถูกส่งไปยังบริการนั้น ใช้เฉพาะเมื่อกด Enter หรือกดแถว "ค้นหาเป็นชื่อสถานที่" ไม่ค้นระหว่างพิมพ์ ตามนโยบายการใช้งานของ OSM)
- **เส้นเชื่อมสถานีตามแม่น้ำ** จัดกลุ่มตามชื่อแม่น้ำ+ลุ่มน้ำ เรียงตามระดับท้องน้ำ (สูง=ต้นน้ำ) เชื่อมสถานีที่ห่างกันไม่เกิน 80 กม. สีตามสถานะที่แย่กว่าของสองปลาย เป็นเส้นตรงระหว่างสถานี **ไม่ใช่แนวแม่น้ำจริง** และการเรียงต้นน้ำ-ปลายน้ำเป็นการประมาณ

## ใช้งานบน LINE ให้สะดวกขึ้น
- **ข้อความแบบการ์ด (Flex):** แจ้งเตือน/สถานะ/สรุปเช้าส่งเป็นการ์ดสี พร้อมแถบระดับน้ำ แนวโน้ม และปุ่มเปิดรายงาน ทุกการ์ดส่งคู่กับข้อความธรรมดา ถ้า LINE ปฏิเสธการ์ด (HTTP 400) ระบบส่งข้อความธรรมดาแทนทันที จึงไม่มีทางที่การ์ดเสียทำให้แจ้งเตือนหาย
- **ตั้งค่าส่วนตัว** พิมพ์ `ตั้งค่า` จะมีปุ่มให้แตะ: `แจ้งทุกระดับ` / `แจ้งเฉพาะเตือนภัย` (เฉพาะตอนถึงหรือพ้นระดับเตือนภัย), `ไม่รบกวนกลางคืน` / `แจ้งกลางคืน` (22:00–06:00 ไม่ส่งยกเว้นเตือนภัย ข้อความที่ค้างส่งหลัง 06:00), `ปิดสรุป` / `เปิดสรุป` ส่งตำแหน่งใหม่ไม่ทำให้ค่าที่ตั้งไว้หาย
- **ใช้ในกลุ่ม/ห้องแชต LINE:** เพิ่มบอตเข้ากลุ่ม แล้วพิมพ์ `ติดตาม อยุธยา` (ชื่อจังหวัดบางส่วนได้ ถ้าตรงหลายจังหวัดบอตจะถามให้ชัดขึ้น) ทั้งกลุ่มจะได้สรุปจังหวัดนั้นทุกเช้า 07:00 คำสั่งอื่น `รายงาน` `ปิดสรุป` `เปิดสรุป` `ยกเลิก` `ช่วยเหลือ` บอตไม่ตอบแชตทั่วไปในกลุ่ม และลบข้อมูลกลุ่มเมื่อถูกเอาออกจากกลุ่ม กลุ่มได้เฉพาะสรุปเช้า ไม่ได้แจ้งเตือนเมื่อสถานะเปลี่ยน
- **Rich menu (ปุ่มใหญ่ใต้ช่องแชต):** ภาพกับนิยามอยู่ที่ `richmenu/` ตั้งบนบัญชี LINE OA ด้วยคำสั่งนี้ในเทอร์มินัลของคุณ (พิมพ์ token เอง สคริปต์ไม่แสดง token):
  ```bash
  export LINE_CHANNEL_TOKEN='...'
  .venv/bin/python richmenu/setup_richmenu.py --delete-old
  ```

## ฐานข้อมูล
ไม่ตั้งอะไร = SQLite ที่ `water.db` (หรือ `WATER_DB`) ตั้ง `DATABASE_URL=postgresql://...` = Postgres ชุดทดสอบ `test_postgres.py` รันกับ Postgres จริง (ผ่านแพ็กเกจ `pgserver`)

## Deploy บน Vercel + Neon (Postgres)
1. push โปรเจกต์ขึ้น GitHub แล้ว Import ที่ Vercel (ไฟล์ `pyproject.toml` ชี้ entrypoint, `vercel.json` ตั้ง region `sin1`)
2. Vercel → Storage / Marketplace → เพิ่ม **Neon** ให้โปรเจกต์ จะได้ env `DATABASE_URL` มาเอง (ควรเป็น URL แบบ pooled) และเลือก region สิงคโปร์ให้ตรงกับฟังก์ชัน
3. ตั้ง env เพิ่มใน Vercel: `CRON_SECRET` (สตริงสุ่ม ≥16 ตัว) และถ้าจะแจ้งเตือน `LINE_CHANNEL_TOKEN`
4. Deploy แล้วตั้งตัวเรียก `/api/cron/ingest` ทุก 20 นาที เลือกอย่างใดอย่างหนึ่ง:
   - **ฟรี (Hobby):** Vercel Cron ฟรีรันได้วันละครั้ง และ expression ที่ถี่กว่านั้นทำให้ deploy ล้มเหลว จึงใช้ `.github/workflows/ingest.yml` แทน: ตั้ง repo secret `CRON_SECRET` (ค่าเดียวกับ Vercel) และ repo variable `APP_URL`
   - **ตัวตั้งเวลาภายนอก (เช่น cron-job.org) ซ้อนเป็นตัวสำรอง:** ตั้ง env `CRON_SECRET_EXTERNAL` (ค่าสุ่มแยกจาก `CRON_SECRET`) แล้วให้บริการนั้นเรียก `GET /api/cron/ingest` พร้อมหัว `Authorization: Bearer <ค่านั้น>` ทุก 20 นาที ลบ env นี้เพื่อเพิกถอนทันทีโดยไม่กระทบ GitHub (รันซ้อนกันได้ปลอดภัย: มีล็อกและข้อมูลไม่ซ้ำ)
   - **Pro:** เพิ่มใน `vercel.json` แล้ว Vercel จะส่ง `Authorization: Bearer $CRON_SECRET` ให้เอง
     ```json
     "crons": [{ "path": "/api/cron/ingest", "schedule": "*/20 * * * *" }]
     ```
5. เปิด `https://<โดเมน>/health` ดู `ingest_ok` ต้องเป็น `true` หลังรันรอบแรก

เพิ่มผู้รับแจ้งเตือน (รันจากเครื่องคุณ ชี้ DB ของ Neon):
```bash
DATABASE_URL='postgresql://...' .venv/bin/python notify.py add --channel line --target <userId> --lat 14.2 --lng 99.0 --label บ้าน
```
ข้อควรรู้: cron ส่งซ้ำหรือพลาดได้ (best effort) ระบบจึงออกแบบให้รันซ้ำได้ปลอดภัย (ข้อมูลไม่ซ้ำ + ล็อกกันรันซ้อน)

## Deploy ด้วย Docker (ทางเลือก ใช้ SQLite + volume)
```bash
docker build -t nam-klai-baan-chan .
docker run -p 8000:8000 -v nkb-data:/data -e LINE_CHANNEL_TOKEN=... nam-klai-baan-chan
```
`INGEST_EVERY` (วินาที, ค่าเริ่มต้น 1200) และ `THRESHOLDS_FILE` ปรับได้ผ่าน env ใช้ SQLite ไฟล์เดียวจึงรัน instance เดียวพร้อม volume เท่านั้น (หรือใส่ `DATABASE_URL` ให้ใช้ Postgres)
